## What changed

Replaced the dead Formspree path (`NEXT_PUBLIC_FORMSPREE_ID` was never set, so submissions went
nowhere) with a server-side Resend integration, following the house pattern in
`/Users/k13/Desktop/PROJECTS/TLC/tlc-web/src/app/api/contact/route.ts`.

1. **`app/api/catering/route.ts`** (new). Server-only env: `RESEND_API_KEY`,
   `CATERING_TO_EMAIL`, `CATERING_FROM_EMAIL`. Ported from the TLC pattern: sanitize/strip
   control chars, subject built server-side only (client `_subject` is never trusted), 16KB
   body cap checked before parsing, per-IP sliding-window rate limit (5/hour, best-effort per
   warm instance), and a 503 `not_configured` response so an unset env fails the submission
   instead of lying to the visitor. This is the **first serverless function** in a repo that
   was previously 100% static (12 prerendered routes); confirmed in the build output below.

   Project-specific additions, all verified working (see Verification):
   - **Retry with exponential backoff**, 3 attempts, ~5s total budget, so a visitor is never
     stranded past that on a serverless execution ceiling. Backoff is 400ms then 900ms between
     attempts, each attempt individually capped so a hung request can't eat the whole budget.
   - **Idempotency key**, one `crypto.randomUUID()` generated per POST, reused across every
     retry attempt for that submission, passed as `{ idempotencyKey }` (Resend Node SDK's
     documented second-argument option, mirrors the `Idempotency-Key` HTTP header). Confirmed
     this is real Resend API surface, not invented: https://resend.com/docs/dashboard/emails/idempotency-keys.
     Kept 24h server-side by Resend. A retry after a lost response cannot double-deliver.
   - Errors Resend marks non-retryable (bad key, rejected sender, validation errors) short
     circuit immediately rather than burning the retry budget, verified below.
   - `Reply-To` set to the enquirer's email, THG can hit reply directly.
   - `_gotcha` honeypot checked first, before rate limiting and before body-size-driven parsing
     of anything else, so bot traffic gets a fast fake-success path without spending a real
     visitor's rate-limit budget.
   - **Single recipient only**, `CATERING_TO_EMAIL`. No K13 archive copy, per Kazim's standing
     rejection of concentrating client submissions in a K13 inbox.

2. **`components/CateringPanel.tsx`**. Now posts JSON to `/api/catering` instead of Formspree.
   Removed the dead `NEXT_PUBLIC_FORMSPREE_ID` check and the Formspree-only hidden `_subject`
   field. On any failure (network error, validation, `not_configured`, `send_failed`), the form
   renders a `mailto:` link pre-filled with everything the visitor typed (name, phone, email,
   party size, date, time, occasion, service type, description), built client-side from a
   snapshot taken at submit time (`lastAttempt` state), so a dropped submission costs the
   visitor a click to their email client, not their typed effort.

3. **`.env.example`**. Removed `NEXT_PUBLIC_FORMSPREE_ID`, added `RESEND_API_KEY`,
   `CATERING_TO_EMAIL`, `CATERING_FROM_EMAIL` with setup notes: scope the key
   `sending_access` to this project's `domain_id`, verify a sending subdomain (not the root),
   explicitly notes this does not touch lobsterlab.us's existing root Google Workspace SPF.

4. **`app/privacy/page.tsx`**. The "who we share it with" section named Formspree as the
   processor for catering submissions; that was already untrue in practice (nothing was
   configured) and would have become untrue in principle the moment this shipped. Swapped to
   Resend, in the same change as the code per instructions. Bumped the effective date (August
   19, 2026) and added a dated changelog comment above it, matching the file's existing pattern
   for the CCPA update. This is a material change (who processes personal information), so
   bumping the date follows the policy's own "Changes to this policy" clause, not just habit.

5. **`README.md`** and **`tasks/todo.md`**. Both referenced the Formspree id as the pending
   client value; updated to describe the Resend values (API key, `catering@` inbox, sending
   subdomain) instead, since leaving them pointed at a provider no longer in the code would
   mislead the next person picking up `todo.md`, which this repo's `CLAUDE.md` names as the
   phased delivery plan of record. Did not touch `docs/reports/` (dated, archival, not source of
   truth) or the pre-existing stale port reference in `README.md` (`:9151`, unrelated drift).

## Verification (actual output, not assumed)

- `npx tsc --noEmit`, clean, no output.
- `npm run build`, clean, 13 routes. `/api/catering` shows as `ƒ (Dynamic)`, everything else
  stays `○ (Static)`, confirming the static-to-serverless boundary is exactly this one route.
- Smoke-tested the built server on :9154 (killed afterward, confirmed port free via
  `lsof -nP -iTCP:9154 -sTCP:LISTEN`):
  - Honeypot (`_gotcha` set) → `{"ok":true}`, fast path, no Resend call attempted.
  - Valid-shaped payload, no env set → `503 {"error":"not_configured"}`.
  - Missing/invalid fields → `400 {"error":"invalid"}`.
  - 20KB oversized body → `413 {"error":"too_large"}`, rejected before parsing.
  - Rate limit: 6th request within the hour from one IP → `429 {"error":"rate_limited"}`,
    matches the 5/hour cap exactly.
  - **Real Resend call with a garbage API key** (`RESEND_API_KEY=re_invalid_test_key_123`):
    request returned `502 {"error":"send_failed"}` in **0.28 seconds**, not the ~5s retry
    budget, confirming the non-retryable short circuit actually fires against a live response
    rather than just in theory. Server log showed Resend's real error shape:
    `{ statusCode: 401, name: 'validation_error', message: 'API key is invalid' }`, which is
    already in the non-retryable set, so this exercised the real code path, not a guess about
    what Resend returns.
- Checked the whole diff for em dash characters (house style rule), none found in any touched
  file including the new route.
- No new dependency beyond `resend` (`^6.20.0`, npm resolved it from my `^6.16.0` pin to match

## Risks

- **Email logo will 404 until the domain is live.** `LOGO_URL` in the route points at
  `${PRODUCTION_URL}/brand/wordmark-horizontal-white.png` (`https://lobsterlab.us/...`), same
  pattern TLC used for its crest. Harmless (a missing image in the notification email, not a
  broken send) but worth a post-launch glance once the domain cuts over.
- **Rate limiter is per-warm-instance memory**, not shared storage, same documented caveat as
  the TLC route it was ported from. Fine for casual abuse, not a hard guarantee under
  distributed load. If that matters here, Vercel WAF in front of this route is the fix, not a
  code change.
- **No domain/DNS work done.** This ships the code path only. Sending will keep failing closed
  (503) until someone with Resend dashboard access creates the sending-access API key, verifies
  a subdomain, and sets the three env vars in Vercel. That is a client/Kazim-side setup step,
  not a code gap.
- **Phone validation is loose by design** (>= 7 digits, no country-code assumptions). Flagging
  in case QA wants a tighter rule for a specific market.
