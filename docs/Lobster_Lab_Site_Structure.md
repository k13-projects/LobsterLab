# Lobster Lab — Site Map & Rebuild Blueprint
**Prepared for:** Tiger Hospitality Group
**Source site:** https://lobsterlab.us (built on SpotHopper, website ID **244728**)
**Captured:** July 28, 2026 · **SpotHopper access ends:** August 1, 2026

This document maps the entire existing lobsterlab.us site — every page, its content, its structure, and every third-party dependency — and lays out a recommended front-end and back-end architecture to rebuild it from scratch using the captured data. Companion files (raw content, structured menus, image manifest, download script, visual diagram) are referenced throughout and shipped alongside this doc.

---

## 1. Executive summary

lobsterlab.us is a **single-location marketing site** for the Carlsbad / Windmill Food Hall Lobster Lab, generated by SpotHopper. It is small (8 routes), content-light, and leans on embedded third-party tools for its interactive features. The rebuild is very achievable before/after the Aug 1 cutoff because:

- **The only content with real substance is the food menu** (24 items, fully captured) and the business/location info. The drink, specials, and events pages are live placeholders ("we are updating").
- **Online ordering (Toast) and catering orders (EZCater) are external** and keep working regardless of SpotHopper — you just re-link them.
- **What you actually lose on Aug 1:** the SpotHopper-hosted embeds (catering inquiry form, private-parties form, jobs portal) and the images/video hosted on SpotHopper's CDN. The forms are trivial to replace; the images must be downloaded now (see `images/download_images.sh`).

**Biggest time-sensitive risk:** the images and promo video live on `static.spotapps.co` / `cdn.spotapps.co`. Pull them before Aug 1.

## 4. Content model (what the "data" is)

The site is data-light. A rebuild only needs a handful of content types:

**`MenuItem`** — the core entity.
```
{ section, name, description, variants: [ { label, price } ] }
```
(24 items captured in `menus/food_menu.json`.)

**`Location`**
```
{ name, address, city, state, zip, status, hours, orderUrl, mapPlaceId, hasDedicatedPages }
```
(5 locations captured in `data/locations.json`.)

**`Page`** (for the CMS-editable marketing pages)
```
{ slug, title, heroImage, bodyBlocks[], seoTitle, seoDescription }
```

**`SiteSettings`** — brand name, tagline, logo, social links, contact email, newsletter provider key.

That's the whole back-end domain. Everything else (ordering, catering checkout, reviews) is delegated to third parties.

## 6. Recommended rebuild architecture

Two viable paths depending on who maintains it.

### Option A — No-code / low-code (fastest, non-technical owner)
- **Platform:** Squarespace, Wix, or a restaurant-specific host (e.g. BentoBox, Popmenu).
- **Menu:** enter the 24 items from `food_menu.json`; or embed Toast's menu.
- **Forms:** built-in form builder → routes to `info@lobsterlab.us`.
- **Ordering/catering:** button links to Toast / EZCater.
- **Pros:** live in a day, no developer. **Cons:** less control, monthly fee.

### Option B — Custom front-end (recommended if you want full control & to unify all 5 locations later)

**Front-end**
- **Framework:** Next.js (React) or Astro — static-first, great SEO, cheap hosting.
- **Styling:** Tailwind CSS.
- **Hosting:** Vercel or Netlify (free/low tier; auto HTTPS; deploy from Git).
- **Pages:** the 7 routes above + a `/[location]` template so Del Mar, San Clemente, Little Italy, and UCSD can each get a page later without new code.
- **Assets:** self-host the downloaded images/video in `/public`; use Next/Image or responsive `<img>`.

**Back-end / data**
- **Content source:** start with local JSON/Markdown (the files in this archive drop straight in). Graduate to a headless CMS — **Sanity**, **Contentful**, or **Payload** — when non-devs need to edit menus/hours. A headless CMS gives you the `MenuItem`, `Location`, and `Page` models from §4 with an admin UI.
- **Forms:** a serverless function (Vercel/Netlify Functions) or a form service (Formspree, Basin) that emails `info@lobsterlab.us` and/or writes to a CRM. Add spam protection (honeypot + reCAPTCHA/Turnstile).
- **Newsletter:** Mailchimp or Klaviyo embed/API.
- **Ordering & catering:** remain external (Toast, EZCater) — no backend needed.
- **Analytics/SEO:** Google Analytics + Google Search Console; re-submit `sitemap.xml`; set the 301 redirects from §2.

**Suggested repo layout (Option B)**
```
/app (or /pages)      → route components for the 7 pages + /[location]
/components           → SiteHeader, SiteFooter, Hero, Gallery, MenuSection, ...
/content
   /menus/food.json   ← from this archive
   /data/locations.json, business_info.json
/public/images        ← downloaded assets
/public/videos
/lib                  → form handler, cms client
```

**Data flow (Option B)**
```
Visitor ─▶ Next.js/Astro pages (static)
              │  reads
              ▼
        Content (JSON now → headless CMS later)
              │
   ┌──────────┼───────────────┬───────────────┐
   ▼          ▼               ▼               ▼
 Toast     EZCater      Form function     Newsletter
(ordering) (catering)   → email/CRM       (Mailchimp)
```

## 7. Rebuild checklist (priority order before/after Aug 1)

**Do before Aug 1 (you lose these):**
1. Run `images/download_images.sh` → save all images + the promo video.
2. Export newsletter subscribers and any form submissions from the SpotHopper dashboard.
3. Confirm you own the **`lobsterlab.us` domain/DNS** at your registrar (not locked inside SpotHopper). If DNS is managed by SpotHopper, move it to your own registrar/Cloudflare now — this is the single most important item.
4. Save Toast + EZCater admin logins and their public URLs.

**Rebuild (after you have the above):**
5. Stand up the new site (Option A or B) using this archive's content.
6. Recreate the 7 pages; wire Toast/EZCater buttons; build catering, parties, and jobs forms.
7. Publish menu from `food_menu.json`; add hours/contact/locations.
8. Point `lobsterlab.us` DNS to the new host; set 301 redirects; re-submit sitemap to Google.
9. QA on mobile; run an accessibility pass (keep the WCAG AA statement).
